# CRLF 隐性故障：一次「能跑 ≠ 会跑」的比较

**日期**：2026-09-11
**触发场景**：新增 `script/sync-to-win.sh`（Windows 侧写、WSL 侧执行）时冒出 `LF will be replaced by CRLF` 警告

## 问题描述

git 在 `git add` 时打印了一条警告：

```
warning: in the working copy of 'script/sync-to-win.sh', LF will be replaced by CRLF
```

很容易被当成噪音忽略 —— 因为脚本**当场就能跑**。但这条警告是真的：Windows 侧 `core.autocrlf=true`，文件只要经过一次检出就会变成 CRLF，而 WSL/容器里执行带 `\r` 的脚本必然失败（`/usr/bin/env: 'bash\r'`）。

## 比较一：三种状态，两种结局

| 状态 | blob（git 存储） | 工作区文件 | WSL 能否执行 |
| --- | :---: | :---: | :---: |
| 全仓库无 `.gitattributes` | LF | CRLF | ✗ |
| 刚写完、尚未 checkout | LF | LF | ✓ **假象** |
| `.gitattributes` 声明 `eol=lf` | LF | LF | ✓ 稳定 |

**关键差别**：前两行的 blob 完全一样（都是 LF），差别只在工作区。所以「现在能跑」不能证明任何事 —— 真正的判据是 **checkout 之后**还能不能跑。

实测：`rm` 掉文件再 `git checkout --`（强制重写），脚本立刻变成 **198 个 CR**。

## 比较二：两种修法

| 修法 | 作用域 | 能否随仓库传播 | 精确度 |
| --- | --- | :---: | --- |
| `git config core.autocrlf false` | 本机全部仓库 | ✗（只在本机生效） | 一刀切 |
| **`.gitattributes`（选定）** | 本仓库、按文件类型 | ✓（clone 即生效） | 可精确到 `*.sh` |

选 `.gitattributes` 的理由：换行符是**仓库属性**，不是个人偏好。CI、容器、别人的 WSL 都该拿到同一份字节。

```ini
# .gitattributes
*.sh          text eol=lf
Dockerfile    text eol=lf
.dockerignore text eol=lf
```

## 比较三：谁更危险

| 文件 | 原状态 | 后果 |
| --- | --- | --- |
| `script/sync-to-win.sh` | 新写，LF（未检出过） | 下次检出即坏 |
| `script/push.sh` | w/crlf（52 个 CR） | 早就带病 |
| `Dockerfile` | w/crlf（53 个 CR） | 旧版 builder 下续行符 `\` 失效 |
| `.dockerignore` / 两个 `verify.sh` | w/crlf | 容器内执行失败 |

**Dockerfile 比脚本更阴**：`.sh` 坏了会当场报错，Dockerfile 的 CRLF 可能只是让某条 `RUN` 静默变了行为。

## 关键发现

- **警告即预兆**：git 说「will be replaced」时，就该当成故障预告，而不是噪音。
- **检测手段**（比肉眼看可靠）：

  ```bash
  git ls-files --eol <file>          # i/lf  w/crlf  attr/  ← 一眼看穿
  tr -cd '\r' < file | wc -c         # 工作区里 CR 的字节数，本该是 0
  ```

- **`.gitattributes` 生效后 `git checkout -- <file>` 不会重写文件**（git 认为内容无变化），必须 `rm` 后 checkout，或用 `git checkout-index -f`。
- **属性生效前 commit 是安全的**：blob 里始终是 LF，坏的一直只是工作区副本。
