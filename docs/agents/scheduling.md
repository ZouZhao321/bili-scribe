# 调度策略

## 队列调度规则

Worker 每 30 秒检查一次队列，逐个判定下列条件：

- **CPU 感知**：CPU 使用率低于阈值时才取任务执行。单 worker 用 50%，多 worker 按并发数提高、上限 95%
- **内存感知**：以容器 cgroup 限额减去当前用量作为可用内存，可用内存需要达到模型需求的 90%，并扣除并发线程已经预留的模型内存
- **并发预留**：线程通过资源判定时把即将加载的模型内存登记到共享的预留计数，避免多个线程各自读到同一份「资源充足」的结论后同时加载模型
- **强制终止的重做上限**：任务被强制终止（内核 OOM、容器被普通信号终止）后重新开始执行的次数上限为 3 次，达到上限停在 `failed` 并说明原因
- **OOM 击杀信息**：容器 cgroup 记录到 `oom_kill` 时，失败原因里会写明这一点。`oom_kill` 是容器生命周期内的累计值，重启不会重置，因此它只用于描述原因，不参与是否重做的判定
- **超时保护**：任务运行超过 6 小时视为僵死，标记为 `failed`

任务停在 `failed` 后不会自动重做，需要调用 `POST /api/v1/tasks/{task_id}/retry` 重新入队，该接口会把重做次数清零。

## 容器内存预算

单个转录线程需要独占一份 Whisper 模型内存，因此容器内存限额的下限是：

```
BILI_SCRIBE_WORKERS × 对应模型的单份内存需求
```

低于该下限时转录进程会被内核 OOM 击杀，容器按 `restart: unless-stopped` 反复重启。Worker 启动时会报告限额、单线程预算以及在该配置下必然超限的模型。

## 模型内存需求（队列调度用）

| 模型 | 最小可用内存 | 说明 |
|------|:-----------:|------|
| tiny | 500 MB | 75MB 模型 + 开销 |
| base | 1.0 GB | 141MB 模型 + 开销 |
| small | 2.0 GB | 464MB 模型 + 开销 |
| medium | 3.5 GB | 1.5GB 模型，RSS ~3GB |
| large-v3 | 5.5 GB | 2.9GB 模型，RSS ~5GB |

单线程建议的容器限额：tiny/base 1GB，small 2GB，medium 4GB，large-v3 6GB。
