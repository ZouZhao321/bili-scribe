# ADR 0008: Whisper 内存管理与 Swap 配置

## 状态

已接受（2026-07-30）

## 背景

在 3.6GB RAM 的云服务器上运行 medium（1.5GB）和 large-v3（2.9GB）模型时，系统频繁卡死。需要理解 faster-whisper 的内存行为并找到解决方案。

## 实验发现

### 模型加载机制

faster-whisper（CTranslate2）使用 **mmap（内存映射文件）** 加载模型：
- 模型文件不是一次性全部读入物理内存（RSS）
- 而是映射到虚拟地址空间，按需按页加载到物理内存
- 物理内存不够时，OS 自动将不常用的权重页换出到 Swap

### 音频处理

- 音频是全部加载到内存，不是流式读取
- 但 5 分钟音频的特征仅 ~5MB，占比极小
- 长视频（1小时）特征约 60MB，依然不是瓶颈
- **模型权重是内存占用的绝对大头**

### 卡死根因

**卡死的根本原因不是模型太大，而是 Swap 太小。**

当物理内存不足时：
1. OS 需要将不常用的模型权重页换出到 Swap
2. 如果 Swap 已满 → 无法换出 → 内存分配失败
3. 系统进入 thrashing（抖动）状态，反复尝试换页，I/O 占满
4. 所有进程（包括 SSH）都得不到响应 → 卡死

## 决策

### 增加 Swap 到 4GB

- 默认 Swap 1.9GB → 加大到 4GB
- 验证结果：large-v3 稳定运行，系统全程响应正常

### 队列层增加内存感知调度

- 仅当可用内存 ≥ 模型需求 90% 时才执行任务
- 避免在内存紧张时启动模型加载

### 模型内存需求表

| 模型 | 磁盘大小 | 虚拟内存映射 | 实际物理内存需求 | 调度阈值 |
| ------ | :-------: | :----------: | :--------------: | :------: |
| tiny | 75MB | ~75MB | ~75MB | 500 MB |
| small | 464MB | ~464MB | ~464MB | 2.0 GB |
| medium | 1.5GB | ~1.5GB | ~1.5GB | 3.5 GB |
| large-v3 | 2.9GB | ~2.9GB | ~2.9GB | 5.5 GB |

## 影响

- 正向：large-v3 模型可在 3.6GB RAM 机器上稳定运行
- 正向：内存感知调度防止 OOM 导致的系统卡死
- 约束：Swap 使用会降低转录速度（磁盘 I/O 比内存慢）
- 约束：调度阈值偏保守，可能在某些场景下过度拒绝任务
