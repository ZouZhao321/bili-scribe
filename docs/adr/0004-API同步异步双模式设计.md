# ADR 0004: API 同步异步双模式设计

## 状态

已接受（2026-07-30）

## 背景

转录服务面临两种截然不同的场景：
1. 有字幕的视频 → 秒出（毫秒级），用户期望同步返回
2. 无字幕的视频 → Whisper 转录（分钟级），必须异步处理

需要设计一个统一的 API 接口，自动根据场景选择同步或异步模式。

## 决策

### 模式选择策略

| 条件 | 模式 | 说明 |
| ------ | ------ | ------ |
| 有 CC/AI 字幕 | 同步 | 秒出，直接返回 JSON |
| 强制 `mode=subtitle` | 同步 | 仅字幕，必然秒出 |
| 强制 `mode=whisper` | 异步 | 返回 202，task_id 轮询 |
| Whisper 模型 small 以下 | 同步 | 快速模型可等待 |
| Whisper 模型 medium 以上 | 异步 | 重型模型必须异步 |
| 提供了 `webhook` | 异步 | 显式要求异步回调 |

### 统一端点

- 单个 `POST /api/v1/transcribe` 端点
- 同步返回 200（含结果），异步返回 202（含 task_id）
- 客户端通过 `GET /api/v1/transcribe/:task_id` 轮询结果

### 为什么不是 RESTful 资源拆分？

- **不拆分**为 `POST /api/v1/transcribe/sync` 和 `POST /api/v1/transcribe/async`
- **原因**：模式选择由服务端自动判断，客户端不应关心内部实现细节

## 影响

- 正向：有字幕的视频使用体验极佳（秒出）
- 正向：Whisper 转录不阻塞客户端
- 正向：统一端点简化了客户端集成
- 约束：客户端需要处理两种响应格式（200 vs 202）
