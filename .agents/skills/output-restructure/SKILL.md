# 开发计划编写技能

## 用途

将用户的技术需求转化为结构化的分阶段实施计划，写入 `docs/plan/` 目录供用户审阅。

## 触发条件

- 用户要求写开发计划、实施计划、重构计划
- 用户提到"技术方案"、"实施步骤"、"开发方案"
- 用户描述了一个需要多步骤完成的技术需求
- 用户说"帮我规划一下"、"怎么分步做"

## 计划文档模板

每个计划文档写入 `docs/plan/<slug>.md`，遵循以下固定结构：

### 1. YAML 前置元数据

```yaml
---
title: <中文标题>
status: draft
created: <YYYY-MM-DD>
branch: <feature分支名>
---
```

### 2. 分支结构图

用 ASCII 树形图展示分支和阶段关系：

```
main
│
└─ <feature分支>
   │
   ├─ 阶段一：<阶段名>
   │  ├─ 📝 <type>(<scope>): <commit描述>
   │  ├─ 📝 <type>(<scope>): <commit描述>
   │  └─ 📝 阶段验收
   │
   ├─ 阶段二：<阶段名>
   │  ├─ ...
   │
   └─ 阶段N：<阶段名>
      ├─ ...
```

规则：
- 阶段按依赖关系排序，前阶段完成后才能进入下一阶段
- 每个阶段 2-4 个 commit，粒度适中
- commit 消息遵循 Conventional Commits：`type(scope): 中文描述`
- 最后一条永远为 `📝 阶段验收` 或 `📝 执行<动作>`

### 3. 阶段详情

每个阶段作为二级标题，内容为逐 commit 展开：

```
## 阶段N：<阶段名>

### 📝 Commit: `<type>(scope): <描述>`

**改动文件**：`<文件路径>`

---

#### 🔧 开发

**做什么**：
- <具体改动项 1>
- <具体改动项 2>

**不做什么**：
- <明确排除的边界 1>
- <明确排除的边界 2>

---

#### ✅ 验收

**验收方式**：`pi -p` 独立验收（不修复）

```bash
pi -p "<验收提示词>"
```

验收提示词模板：

```
检测以下内容：
1. <检测项 1>，通过标准：<标准>
2. <检测项 2>，通过标准：<标准>

要求：
- 只检测，不修复
- 通过输出 ✅，不通过输出 ❌ + 原因
```

> ⚠️ 验收由独立的 `pi -p` 会话执行。当前开发 Agent 不得自行验收。

---

### 📝 Commit: `<type>(scope): <描述>`
...
```

### 4. 阶段验收（可选）

如果一个阶段包含多个 commit，在阶段末尾加一个聚合验收：

```
### 📝 阶段验收

**验收方式**：`pi -p` 独立验收（不修复）

```bash
pi -p "检测以下内容：
1. <阶段整体检测项 1>，通过标准：<标准>
2. <阶段整体检测项 2>，通过标准：<标准>

要求：只检测，不修复。通过输出 ✅，不通过输出 ❌ + 原因"
```
```

## 格式说明

### 计划文档结构总览

```
---
YAML 元数据（标题/状态/日期/分支）
---

# 标题

分支结构图（ASCII 树）

## 阶段一
### 📝 Commit 1
  - 改动文件
  - 🔧 开发（做什么 / 不做什么）
  - ✅ 验收（pi -p 提示词）
### 📝 Commit 2
  ...
### 📝 阶段验收（可选）

## 阶段二
  ...
```

### 各部分说明

| 部分 | 位置 | 作用 | 受众 |
|------|------|------|------|
| YAML 元数据 | 文件头 | 记录计划标题、状态 (`draft`/`done`)、创建日期、关联分支 | 项目管理 |
| 分支结构图 | 正文开头 | 一图胜千言，展示分支拓扑、阶段划分、commit 序列 | 审阅者快速了解全貌 |
| 改动文件 | 每个 commit 开头 | 明确指出改动范围，避免改到不该改的文件 | 开发 Agent |
| 🔧 开发 | 每个 commit 中部 | **做什么**约束范围，**不做什么**明确边界 | 开发 Agent |
| ✅ 验收 | 每个 commit 尾部 | 给 `pi -p` 的检测提示词，定义通过标准 | 验收 Agent（独立 pi -p） |
| 阶段验收 | 阶段末尾 | 聚合检测该阶段所有 commit 的整体效果 | 验收 Agent |

### YAML 元数据字段

| 字段 | 必填 | 说明 | 示例 |
|------|:----:|------|------|
| `title` | ✅ | 计划中文标题，简洁描述做什么 | `输出格式重构实施计划` |
| `status` | ✅ | 计划状态：`draft`（草稿/审阅中）或 `done`（已实施完毕） | `draft` |
| `created` | ✅ | 创建日期，ISO 格式 | `2026-08-07` |
| `branch` | ✅ | 关联的 feature 分支名 | `feat/output-restructure` |

### 分支结构图符号

| 符号 | 含义 |
|:----:|------|
| `├─` | 阶段节点 |
| `│ ├─` | 阶段内的 commit 节点 |
| `│ └─` | 阶段内最后一个节点 |
| `└─` | 最后一个阶段 |
| `📝` | 表示一个 commit 或验收步骤 |
| `type(scope): 描述` | Conventional Commits 格式的 commit 消息 |

### Commit 消息格式

遵循 [Conventional Commits](https://www.conventionalcommits.org/)：

```
<type>(<scope>): <中文描述>
```

| type | 使用场景 |
|:----:|----------|
| `feat` | 新增功能、新能力 |
| `fix` | 修复 bug |
| `chore` | 配置变更、日志、依赖更新等非功能改动 |
| `refactor` | 重构（不改变外部行为） |
| `docs` | 文档变更 |

scope 为改动的模块名，如 `queue`、`runner`、`transcriber`、`cli`。

### 验收提示词格式

验收提示词是给独立 `pi -p` 会话的自然语言指令，不是可执行脚本：

```
检测以下内容：
1. <要检测什么>，通过标准：<怎样算通过>
2. ...

要求：
- 只检测，不修复
- 通过输出 ✅，不通过输出 ❌ + 原因
```

**为什么用提示词而不是脚本**：
- 验收 Agent 可以灵活判断（脚本只能做机械检查）
- 提示词更接近自然语言，审阅者也能看懂
- 避免验收脚本本身需要维护的问题

> ⚠️ 验收提示词中必须包含"只检测，不修复"，防止验收 Agent 越权修改代码。

## 编写原则

### 开发与验收分离（核心原则）

**禁止自己开发自己验收**。开发和验收必须由不同的 Agent 实例执行：

- **开发 Agent**：当前会话，负责按计划实现代码
- **验收 Agent**：通过 `pi -p` 启动的独立会话，只负责检测，不负责修复

这样做的好处：
- 避免"既当运动员又当裁判"——自己写的代码自己测，容易漏掉边界 case
- 验收 Agent 没有开发上下文，更接近真实用户视角
- 发现的问题返回给开发 Agent 修复，形成闭环

### 粒度控制

- 每个 commit 是可独立验证的最小改动单元
- 一个 commit 只改 1-2 个文件
- 验收提示词不超过 20 行，超过说明粒度过大，需要拆分

### 边界清晰

每个 commit 必须同时声明 **做什么** 和 **不做什么**：
- "做什么"约束实施范围，避免 scope creep
- "不做什么"明确排除边界，防止过度实现

### 验收驱动

每个 commit 的验收不是直接运行的脚本，而是给 `pi -p` 的提示词：

- 验收提示词描述**要检测什么**和**通过标准**
- 验收 Agent 只做检测（assert/检查），**不修复发现的问题**
- 验收 Agent 输出 `✅` 或 `❌` 及具体原因
- 验收不通过 → 返回开发 Agent 修复 → 修复后重新验收

### 阶段排序

阶段按以下原则排序：
1. 基础设施先行（日志、配置、存储结构）
2. 核心逻辑居中（业务改动）
3. 迁移/清理靠后（数据迁移、旧代码清理）
4. 收尾/上线最后（参数调整、开关切换）

## 输出位置

- 计划文档：`docs/plan/<slug>.md`（唯一输出）
- 验收提示词内嵌在计划文档中，不单独存放脚本文件

## 交互流程

1. 分析用户需求，理清改动范围
2. 设计分支结构和阶段划分
3. 编写完整计划文档，写入 `docs/plan/`
4. 展示计划概述，请用户审阅
5. 根据用户反馈修改，直到确认
6. 确认后，按计划分阶段实施：
   - **开发 Agent**（当前会话）实现代码
   - **验收 Agent**（`pi -p`）独立检测，不修复
   - 验收不通过 → 开发 Agent 修复 → 重新验收
   - 验收通过 → 提交 commit → 进入下一阶段

## 注意事项

- 计划是**草案**，status 始终为 `draft`，用户确认后才开始实施
- 不要一次写完就开始实施，必须先让用户审阅
- 如果用户的需求本身很简单（1-2 个 commit），不需要写计划，直接实施即可
- **严禁开发 Agent 自行验收**——验收必须由独立的 `pi -p` 会话执行
- 验收 Agent 的提示词必须明确写明"只检测，不修复"
